# File map and handoff schema

## Artifacts

Maintain two artifacts:

- An exhaustive TSV ledger generated by `scripts/inventory.py` and completed by
  the agent. It is the coverage authority.
- A narrative Markdown map that explains target architecture, cross-file
  collapses, ordered slices, budgets, invariants, and validation. It is the human
  and agent handoff.

Use user-requested paths. Otherwise keep working artifacts in `.scratch/` and put
the durable handoff in `docs/` only when repository policy treats that as the
appropriate design surface.

## Ledger columns

| Column | Required meaning |
| --- | --- |
| `file` | Repository-relative original path. Never replace it with a directory aggregate. |
| `language` | Inventory classification. |
| `lines`, `nonblank`, `comment_lines`, `branch_tokens`, `assert_tokens`, `bytes` | Deterministic baseline proxies from the inventory script. They guide inspection; they are not deletion quotas. |
| `disposition` | `keep`, `compress`, `deepen`, `merge`, `delete`, `move-private`, `split`, or `generated-asset`. |
| `slice` | Ordered vertical slice that owns implementation of this row. |
| `owner` | One surviving file/module and authoritative fact or lifecycle. |
| `action` | Concrete deletion, consolidation, or retained reason. Name peers/callers. |
| `expected_lines` | Target or expected deletion band, including replacement code. Leave blank when evidence cannot support one. |
| `current_lines`, `delta_lines` | Final reconciliation against the baseline; deleted files use zero current lines. |
| `risk` | Behavior, ABI, ownership, concurrency, lifetime, visual, build, or performance risk. |
| `validation` | Planned evidence owner: focused test, scenario, snapshot, benchmark, build, or justified none for map-only work. |
| `status` | `unreviewed`, `mapped`, `in-progress`, `complete`, `superseded`, or `blocked`. |
| `evidence` | Actual command/result/artifact or the concrete reason validation was unavailable. |

Do not mark a row complete with “simplify,” “clean up,” or “reduce checks.” State
which representation disappears, which owner survives, and why its proof remains
sufficient.

## Dispositions

- `keep`: deliberately irreducible or a justified seam. This is coverage, not a
  missed opportunity.
- `compress`: preserve responsibility in place while deleting duplicate paths,
  states, fields, checks, or comments.
- `deepen`: absorb repeated policy from peers into this surviving owner. Count its
  added lines against deleted peer code.
- `merge`: migrate behavior into the named owner, then delete this file.
- `delete`: behavior is dead, generated elsewhere, or pure forwarding.
- `move-private`: retain real behavior but remove unnecessary public surface.
- `split`: use only when lifecycle/locality improves and total relationships or
  maintained LOC falls; file count alone may rise.
- `generated-asset`: move generated payload out of maintained source with
  provenance, deterministic generation, size/hash checks, and build integration.

## Narrative map

Include:

1. Scope, commit, exclusions, baseline metrics, and target band.
2. Non-negotiable behavior, ownership, concurrency, lifetime, and performance
   invariants.
3. One-fact/one-owner target shape and check/comment policy.
4. Compression budget by vertical slice, expressed as planning bands rather than
   independent per-file quotas.
5. Ordered implementation program with migration and deletion boundaries.
6. Validation contract assigning each invariant to the correct evidence surface.
7. Complete file disposition ledger or a link to the TSV.
8. Coverage reconciliation proving every initial file is represented.

## Vertical-slice record

Before each implementation slice, record:

- exact files and physical LOC before editing;
- at least two concrete repeated cases;
- one surviving representation and owner;
- checks removed and the seam retaining proof;
- allocation, lock, string, virtual-call, wait, and dispatch effects in hot paths;
- borrowed views, storage stability, logical destruction, physical retirement,
  cancellation, and submission/abandon behavior where applicable;
- expected net LOC/file delta;
- smallest complete validation and any baseline limitations.

After the slice, record actual totals and newly created files. Reject apparent
compression that only transfers lines to an uncounted helper.

## Coverage reconciliation

Compare the initial inventory, final inventory, and ledger:

- every initial file has one disposition;
- every deleted path names its surviving owner or dead/generated reason;
- every new file is counted and justified as a deep owner;
- retained files are explicit;
- ledger totals equal the defined scope after exclusions;
- superseded targets and architectural exceptions carry evidence, not silence.
